## 1. 背景与问题

仓库当前只有 `ZhangIvan` 一个维护账号。继续把第二位人类 reviewer 作为所有高风险仓库变更的绝对前置，会使代码、治理和证据 PR 永久无法合并；直接取消 review、required checks 或分支保护又会失去独立审阅和可追溯性。

本决策选择“单维护者决策 + 独立 Agent 验证 + owner attestation + exact-candidate-bound CI + 稳定窗口 + 合并后证据”。它只改变仓库内合并责任，不把 Agent 描述成人类审批人，也不把“merge”解释成“deploy”或“production approved”。

## 2. 角色与术语

- **Decision owner**：`ZhangIvan`，负责最终仓库合并决策、范围声明和风险接受。
- **Verifier**：未参与被审切片实现、使用独立上下文并输出独立报告的 Agent。Verifier 提供审阅证据，不提交 GitHub `APPROVED`，不冒充人类或外部审批人。
- **Owner attestation**：owner 对精确 base/head/tree、范围、风险、验证、例外和回滚的绑定声明。它不计入独立 verifier quorum。
- **GitHub approval**：GitHub Pull Request Review 的 `APPROVED` 状态。当前 `required_approving_review_count=0`；这项平台配置与治理 verifier quorum 是两套不同概念。
- **Trusted-control audit**：主 Agent 与独立 verifier 对 changed paths、全部 workflow 定义、workflow blob/tree、触发事件、权限、固定 action、命令、required context/app、run/job ID、exact head/base、日志和保护快照进行的失败关闭审计。它不是一个未定义的外部审批人。
- **Candidate head**：PR API 的精确 `head.sha`；required check-run 的 `head_sha` 必须等于该值。
- **Execution object**：workflow 实际 checkout 并执行的 commit。`pull_request` 事件默认可以是 `refs/pull/<n>/merge` 的 synthetic merge commit，因此 execution SHA 不要求等于 candidate head；两者必须按第 7 节分别绑定。
- **稳定窗口**：最终候选和证据固定后的连续观察期。窗口用于发现漂移，不替代功能、安全或生产验证。

## 3. 选项与决定

考虑过三种路径：

1. 继续等待第二位人类维护者：最小权限，但在当前单账号事实下无限期阻塞。
2. owner 直接合并且不要求独立证据：可执行，但无法满足独立 review 与审计要求。
3. owner 保留决策权，由独立 Agent 验证并绑定不可变候选：在当前权限约束下可执行，并保留失败关闭、可追溯和分支保护。

选择第 3 种。**只有本决策变为 `ACTIVE` 后**，`ZhangIvan` 才可以按本决策提交并合并自己的常规 PR，并且必须满足风险分级、独立验证、owner attestation、required checks、稳定窗口和合并后证据。任何情况下都不得使用 admin bypass、force push、直接推送 `main`、删除保护规则或临时降低门禁来制造可合并状态。

## 4. 治理变更风险等级

`CR` 表示 **Change Risk**，与产品/发布路线的 `R0–R8` 无关。等级按累计 diff 的语义影响判定，不能因为文件扩展名是 `.md` 就降级；未知或跨级变更采用最高适用等级。

| 等级 | 语义边界 | 最低仓库门禁 |
| --- | --- | --- |
| `CR0` | 纯索引、排版或既有不可变证据指针；不改变规范、控制或运行语义 | 一路独立 Agent、相关检查、最终 API/diff 快照 |
| `CR1` | 测试、机械重构或低风险工具调整；不改变公开接口、安全、依赖、CI 或运行行为 | 一路独立 Agent、相关测试与 required checks、owner attestation |
| `CR2` | 普通行为或 API 变化，且不进入下列高风险域 | 两路独立 Agent、完整检查、exact-candidate 快照、owner attestation |
| `CR3` | 治理、CI/workflow/validator、依赖/供应链、鉴权、租户、state/migration、admission、usage、Provider route、删除、公开契约、安全或生产配置语义 | 两路 fresh 独立 Agent、trusted-control audit、完整 required checks、owner attestation、至少 10 分钟稳定窗口 |
| `CR4` | 真实外部/生产状态、凭据、客户数据、不可逆操作、部署、release/tag 或流量变更 | 仓库变更至少按 `CR3`；真实操作另需对应人工/外部门和逐动作明确授权 |

`CR4` 不是“更严格的自合并”。Agent 和本决策都无权执行或批准真实生产操作；到达外部状态边界必须停止并取得该精确操作的授权。

## 6. 独立审阅协议

1. 每份 review 绑定同一 exact base SHA、head SHA、tree SHA 和完整累计 diff。
2. “fresh”要求独立上下文、独立输出，且 reviewer 未参与该切片实现；同一报告重放或同一 Agent 自审不计数。
3. Reviewer 分别检查验收、越界、漏测、安全/隐私/兼容性、错误成功假设和回滚。
4. 主 Agent 负责复验 Agent 结论；Agent 的“完成”不自动改变 PR 或 Goal 状态。
5. head/base/tree、diff、workflow、保护规则或验证输入变化后，旧 review 立即失效。
6. Owner 可以接受合规 `Finding-P1` residual，但不计入独立 reviewer quorum，也不能把自己的 attestation 写成外部 approval。

每份 `gvn-agent-reviews-v1` review 必须完整保存 canonical task/reviewer ID、实际模型与推理档位、`implementation_participant=false`、起止时间、base/head/tree、verdict/P0/P1/P2、固定 review scope、`verified/inferred/unverified` 三分清单、验证命令/结果/证据、结构化 P2 dispositions、完整 review input/body 及二者 SHA-256。完成时间不得晚于 pre-attestation cutoff；两份 reviewer、input 和 report 必须不同且按 reviewer ID 排序。PR #19 与 activation evidence PR 的两份 review 还必须把固定项 `stable-window capture-time freshness (GVN-P1-005)` 列入 `unverified`，且 `verified` 不得声称该 freshness 已验证。当前运行时无法为 orchestrator transcript 提供第三方密码学 receipt 的边界仍由 `GVN-P1-003` 透明管理，结构完整不等于来源真实性已被技术证明。

## 7. 每个 self-merge PR 的必备证据

合并前至少记录并核验：

- PR 号、标题、base/head/tree、changed paths 和风险等级；
- 实际 required contexts、check-run `head_sha`、app、run/job ID、event、workflow path、attempt 和结论；对于 `pull_request` synthetic execution，还要从不可变 run log 取得 execution SHA，并由 Git commit API 核验其有序 parents 精确为 `[base, candidate_head]` 及其 execution tree；不得把 synthetic execution 简写为“裸 head 被执行”
- 与风险等级相符的独立 Agent 报告，区分已验证、推断和未验证；
- 未解决 discussion、review request、dismissed/stale review、label、draft、auto-merge 和 merge queue 状态；
- owner attestation：范围、风险、checks、reviews、trusted-control audit 结果、例外、未知项、回滚、无生产授权、PR body 原始字节 hash 和下述 `gvn-pre-attestation-v1` 根；
- 普通受保护合并方式、expected head、临门 base 和合并后证据位置。

PR 正文、评论、label 和 review 状态都是可变指针，不能单独作为事实。必须以 GitHub API、Git 对象和执行日志绑定候选。缺失、网络失败、权限不足或来源无法确认时记为 `INCONCLUSIVE`/`PENDING`，不得改写为 `PASS`。

### 7.1 exact-candidate 与 execution 绑定

`candidate_head`、`check_run.head_sha` 和 `execution_sha` 是三个独立字段。前两者必须相等；每个 required job 必须向自身日志输出且只输出一条结构化 `GVN_EXECUTION context=<context> sha=<execution_sha> tree=<execution_tree> parents=<base> <candidate_head>` 结果标记，以及一条 `GVN_RUNNER` 标记，绑定 `ubuntu-24.04`、Linux/X64、非 unknown image OS/version、`ZhangIvan/QingYin`、`pull_request` 与 `shallow=false`。Validator 必须从与该 job ID 对应的 UTF-8 日志成员解析并逐字段匹配 provenance。若 execution 是 synthetic merge commit，则再由 Git API 证明对象类型为 commit、有序 parents 精确为 `[base, candidate_head]` 并记录 execution tree；任一对象、顺序、tree、run/job/log/marker 绑定缺失、额外对象或 marker 重复即 `INCONCLUSIVE`。五个 context/check-run/job/execution/log 必须精确闭合，check-run/job/external ID 唯一；同一 workflow 的 run/suite ID 可以依法共享但不得出现未被 provenance 引用的 run。测试的是 base 与 candidate 的合并结果，不得声称 workflow 直接执行了裸 candidate head。

### 7.2 `canonical-json-v1` 与非循环 attestation

稳定窗口使用版本固定的 `gvn-manifest-v1` 分组件 evidence manifest。每个 GitHub endpoint 同时记录 HTTP 解码后 response body 的原始 UTF-8 字节 SHA-256 与完整 decoded JSON 经 `canonical_json_v1` 序列化后的 SHA-256；不再使用可由不同 verifier 自选字段的模糊 projection。任何一项变化都重置证据。`gvn-endpoint-bundle-v2` 的每个 response envelope 还必须携带独立 `human_body_hashes` sidecar；每项恰含 `kind,immutable_id,field="body",state,sha256`，`state` 只能是 `missing/null/string`，前两者的 `sha256=null`，`string` 则必须等于对应 decoded API `body.encode("utf-8")` 的 SHA-256。Human label 必须使用 JSON，并先存在正确的对象/数组/GraphQL container 与 immutable ID；`missing` 只能表示合法对象存在但 `body` 键缺失，不能把整个人类对象、pullRequest、thread/comment container 缺失伪装成空 sidecar。该 hash 不 trim、不改 CRLF/尾空格、不加入 CLI 终端换行、也不自行做 NFC 变换；但整个 evidence 输入仍须满足下段全局 NFC 约束。Sidecar 不复制额外正文，也不意味着 package 不含正文：原始 `response_body_base64` 仍包含完整响应。完整响应 raw hash、canonical hash 与字段 hash 三者职责独立，任何一项变化都重置证据。

JSON 规范化使用 RFC 8785 JSON Canonicalization Scheme 的确定性序列化，并进一步限制输入：UTF-8、无 BOM，所有字符串必须已是 NFC；解析时拒绝重复 object key、NFC 后 key 冲突、非法 surrogate、NaN/Infinity；`gvn-manifest-v1` 只允许布尔、null、字符串及 IEEE-754 安全范围内的整数，拒绝浮点、指数和 `-0`。RFC 8785 的 UTF-16 code-unit key 排序、字符串 escaping、compact encoding 与无终端换行规则保持不变。attestation payload 也必须使用同一 serializer。语义有序数组（例如 parents）保持原序；无序集合的 decoded 原始数组必须已经按下表的类型化 key 排序，Validator 不得静默重排后接受。整数 key 必须是非 bool 的安全整数并按数值比较；字符串 key 必须是 NFC、无 surrogate 并按 UTF-16 code unit 比较；复合 key 逐项比较，最后追加完整 `canonical_json_v1(item)` 无符号字节作为确定性 tie-break。每个数组的 immutable unique key 独立校验，不能用 tie-break 掩盖重复身份。schema 版本、字段集合、排序 key 或 serializer 变化都视为新证据输入，旧 manifest 不可复用。

每次请求的 canonical preimage 使用 `gvn-request-v1`：object 必须恰含 `schema="gvn-request-v1"`、`source`、`method`、`authority`、`path`、`query`、`body`；`query` 是按 key/value UTF-16 tuple 排序且不重复的二元字符串数组。`github-api` 只允许 authority=`api.github.com` 与 `GET/POST/PUT`；GET 的 `body=null`，POST/PUT 必须内嵌完整受限 JSON body。`git/agent/derived` 分别固定 authority/method 为 `ZhangIvan/QingYin+READ`、`codex-orchestrator+READ`、`local+DERIVE`；derived 内嵌 canonical input，其他两个 body 为 null。PR/head 路径及 GraphQL owner/name/number variables 必须与 package identity 相等；REST 列表固定请求 `page=1&per_page=100`，数组少于 100 项，带 `total_count` 的对象还必须等于内嵌数组长度，否则按可能存在未采集下一页失败关闭。这样 request hash 的全部 preimage 均在 evidence package 内，不允许只留下不可复算的 body digest，也不能用分页截断隐藏对象。

`gvn-manifest-v1` 的 object 必须恰含 `schema`、`phase`、`repository`、`pr_number`、`base_sha`、`candidate_head`、`candidate_tree`、`snapshot_cutoff_utc`、`component_digests`、`effective_merge_sha`。`phase` 只允许 `stable-window-start`、`stable-window-end`、`post-merge`；前两者的 `effective_merge_sha=null` 且组件固定为下表从 `pr` 到 `attestation`，post-merge 必须使用实际 40-hex merge SHA 并再追加唯一 `merge` 组件。每个 `component_digests` item 只允许 `name`、`endpoint_bundle_sha256`，顺序固定。缺字段、额外字段、重复/未知组件、版本不一致或非秒精度 RFC3339 UTC cutoff 一律 `INCONCLUSIVE`。

为消除 manifest/attestation 相互引用，preimage 依赖必须严格按下列单向 DAG 生成，禁止逆向引用或跳步：

```text
pre-attestation components
  -> gvn-pre-attestation-v1 root
  -> gvn-attestation-v1 payload hash
  -> published comment/API metadata
  -> stable-window gvn-manifest-v1
  -> merge response/post-merge Git+API components
  -> post-merge gvn-manifest-v1
```

## 8. CR3 稳定窗口

`CR3` 候选在最终 head、base、tree、两份 review、owner attestation、所有 required checks 和保护快照固定后，必须稳定至少 10 分钟。窗口起止各取一次独立快照。两个声明 cutoff 的差值和逐组件恒等只证明 window integrity，不证明 capture-time freshness；PR #19 与 activation evidence 只能按 `GVN-P1-005` 得到一次性 `CONDITIONAL_ACCEPTED_RESIDUAL`，普通 `CR3` 必须提供未来 schema 支持的可信 freshness receipt，否则 `--require-merge-ready` 失败关闭。

以下任一变化都会立即使旧证据失效并重置全部 review、checks、attestation、trusted-control audit 和窗口：fast-forward、amend、push/rebase 或 base/head/tree/diff 漂移，即使最终 tree 恰好相同；workflow/validator/依赖/runner image/resolved action/toolchain/lockfile、保护/ruleset、owner/collaborator、security/source-binding 能力变化；trusted-control audit 的输入、结果或证据变化；check rerun 或 check-run 的状态、结论、context、app、head_sha、event、path、attempt、run/job/log/execution provenance 变化；review 提交/编辑/dismiss、review finding 或 discussion 变化；PR title/body/comment/label/draft/review request/auto-merge/queue/mergeability 或任一 manifest component 变化；以及 residual 到期、稳定窗口结束时间跨越 `valid_until`。窗口起止和 post-merge 快照必须使用同一 schema 逐组件一致比较，并从可信 UTC 时间源核对每个 residual 仍在有效期内。

## 9. 生效状态机与 bootstrap 边界

本决策不能授权自身。唯一状态机如下：

```text
PROPOSED / effective=PENDING
  -> 治理 PR 通过普通受保护合并
  -> 仍为 PROPOSED / PENDING
  -> 对已合并治理 commit 做独立、只读 post-merge 验证
```
