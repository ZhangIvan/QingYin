## 1. 背景与问题

仓库当前只有 `ZhangIvan` 一个维护账号。继续把第二位人类 reviewer 作为所有高风险仓库变更的绝对前置，会使代码、治理和证据 PR 永久无法合并；直接取消 review、required checks 或分支保护又会失去独立审阅和可追溯性。

本决策选择“单维护者决策 + 独立 Agent 验证 + owner attestation + exact-head CI + 稳定窗口 + 合并后证据”。它只改变仓库内合并责任，不把 Agent 描述成人类审批人，也不把“merge”解释成“deploy”或“production approved”。

## 2. 角色与术语

- **Decision owner**：`ZhangIvan`，负责最终仓库合并决策、范围声明和风险接受。
- **Verifier**：未参与被审切片实现、使用独立上下文并输出独立报告的 Agent。Verifier 提供审阅证据，不提交 GitHub `APPROVED`，不冒充人类或外部审批人。
- **Owner attestation**：owner 对精确 base/head/tree、范围、风险、验证、例外和回滚的绑定声明。它不计入独立 verifier quorum。
- **GitHub approval**：GitHub Pull Request Review 的 `APPROVED` 状态。当前 `required_approving_review_count=0`；这项平台配置与治理 verifier quorum 是两套不同概念。
- **Trusted-control audit**：主 Agent 与独立 verifier 对 changed paths、全部 workflow 定义、workflow blob/tree、触发事件、权限、固定 action、命令、required context/app、run/job ID、exact head/base、日志和保护快照进行的失败关闭审计。它不是一个未定义的外部审批人。
- **稳定窗口**：最终候选和证据固定后的连续观察期。窗口用于发现漂移，不替代功能、安全或生产验证。

## 3. 选项与决定

考虑过三种路径：

1. 继续等待第二位人类维护者：最小权限，但在当前单账号事实下无限期阻塞。
2. owner 直接合并且不要求独立证据：可执行，但无法满足独立 review 与审计要求。
3. owner 保留决策权，由独立 Agent 验证并绑定不可变候选：在当前权限约束下可执行，并保留失败关闭、可追溯和分支保护。

选择第 3 种。**只有本决策变为 `ACTIVE` 后**，`ZhangIvan` 才可以按本决策提交并合并自己的常规 PR，并且必须满足风险分级、独立验证、owner attestation、required checks、稳定窗口和合并后证据。任何情况下都不得使用 admin bypass、force push、直接推送 `main`、删除保护规则或临时降低门禁来制造可合并状态。

## 4. 治理变更风险等级

`CR` 表示 **Change Risk**，与产品/发布路线的 `R0–R8` 无关。等级按累计 diff 的语义影响判定，不能因为文件扩展名是 `.md` 就降级；未知或跨级变更采用最高适用等级。

| 等级 | 语义边界 | 最低仓库门禁 |
| --- | --- | --- |
| `CR0` | 纯索引、排版或既有不可变证据指针；不改变规范、控制或运行语义 | 一路独立 Agent、相关检查、最终 API/diff 快照 |
| `CR1` | 测试、机械重构或低风险工具调整；不改变公开接口、安全、依赖、CI 或运行行为 | 一路独立 Agent、相关测试与 required checks、owner attestation |
| `CR2` | 普通行为或 API 变化，且不进入下列高风险域 | 两路独立 Agent、完整检查、exact-head 快照、owner attestation |
| `CR3` | 治理、CI/workflow/validator、依赖/供应链、鉴权、租户、state/migration、admission、usage、Provider route、删除、公开契约、安全或生产配置语义 | 两路 fresh 独立 Agent、trusted-control audit、完整 required checks、owner attestation、至少 10 分钟稳定窗口 |
| `CR4` | 真实外部/生产状态、凭据、客户数据、不可逆操作、部署、release/tag 或流量变更 | 仓库变更至少按 `CR3`；真实操作另需对应人工/外部门和逐动作明确授权 |

`CR4` 不是“更严格的自合并”。Agent 和本决策都无权执行或批准真实生产操作；到达外部状态边界必须停止并取得该精确操作的授权。

## 5. Finding 严重度与例外

- `Finding-P0`：安全、数据损失、跨租户、秘密暴露、错误对外行为或不可回滚破坏。不得例外，不得合并。
- `Finding-P1`：功能、契约、治理或关键证据缺陷。默认阻塞；只有具名 owner 记录精确范围、理由、缓解、回滚、证据、有效期和失效条件后才可接受。
- `Finding-P2`：可维护性或非阻断改进。必须记录，不得隐藏为“无问题”。

`Finding-P1` 例外不得覆盖 `Finding-P0`，也不得覆盖 secret、租户隔离、客户数据、不可恢复数据损坏、生产凭据、生产流量或下文六类外部门。无法判定严重度、provenance 或回滚时按更高等级处理。

当前透明 residual `GVN-P1-001`：GitHub required check 能绑定 GitHub Actions app 与 context 名称，但不绑定某个 workflow blob/ref。该限制**未被技术消除**，其接受边界如下：

- `accepted_by`：`ZhangIvan`；该接受仅在本决策 `ACTIVE` 后对常规 PR 生效，owner 只接受仓库 required-check provenance 的残余风险，不计入 verifier quorum。治理 bootstrap PR 和 activation evidence PR 必须使用各自的精确 owner attestation，不能提前引用本项。
- `scope`：本仓库 `CR0–CR3` 的普通受保护 PR 合并证据；不适用于 `CR4` 真实操作、生产、secret、租户、客户数据或外部门。
- `mitigation`：每个 `CR3` 候选执行 trusted-control audit、两路 fresh review、精确 hash、10 分钟稳定窗口和 post-merge evidence。
- `fallback`：任一来源无法确认或门禁失效即停止合并；改用具备不同 app identity 的外部 check、真实独立人类 review 或新的 superseding decision，不能降低保护。
- `valid_until`：2026-09-29，或下列任一事件发生时立即提前失效：owner/collaborator、workflow/validator、required context/app、保护/ruleset、GitHub source-binding 能力、候选风险等级或安全事件变化。
- `review_date`：每个 `CR3` PR 的最终快照时复核，且最迟不晚于 `valid_until`；续期必须形成新的具名 attestation 或 superseding decision。
- `evidence`：CI-B0 PR #18 及每个候选的 exact-head/tree/run/job/log/protection 快照；缺失时为 `PENDING/INCONCLUSIVE`。

## 6. 独立审阅协议

1. 每份 review 绑定同一 exact base SHA、head SHA、tree SHA 和完整累计 diff。
2. “fresh”要求独立上下文、独立输出，且 reviewer 未参与该切片实现；同一报告重放或同一 Agent 自审不计数。
3. Reviewer 分别检查验收、越界、漏测、安全/隐私/兼容性、错误成功假设和回滚。
4. 主 Agent 负责复验 Agent 结论；Agent 的“完成”不自动改变 PR 或 Goal 状态。
5. head/base/tree、diff、workflow、保护规则或验证输入变化后，旧 review 立即失效。
6. Owner 可以接受合规 `Finding-P1` residual，但不计入独立 reviewer quorum，也不能把自己的 attestation 写成外部 approval。

## 7. 每个 self-merge PR 的必备证据

合并前至少记录并核验：

- PR 号、标题、base/head/tree、changed paths 和风险等级；
- 实际 required contexts、check-run `head_sha`、app、run/job ID、event、workflow path、attempt 和结论；
- 与风险等级相符的独立 Agent 报告，区分已验证、推断和未验证；
- 未解决 discussion、review request、dismissed/stale review、label、draft、auto-merge 和 merge queue 状态；
- owner attestation：范围、风险、checks、reviews、trusted-control audit 结果、例外、未知项、回滚、无生产授权；
- 普通受保护合并方式和合并后证据位置。

PR 正文、评论、label 和 review 状态都是可变指针，不能单独作为事实。必须以 GitHub API、Git 对象和执行日志绑定候选。缺失、网络失败、权限不足或来源无法确认时记为 `INCONCLUSIVE`/`PENDING`，不得改写为 `PASS`。

## 8. CR3 稳定窗口

`CR3` 候选在最终 head、base、tree、两份 review、owner attestation、所有 required checks 和保护快照固定后，必须稳定至少 10 分钟。窗口起止各取一次独立快照。

以下任一变化都会立即使旧证据失效并重置 attestation/窗口：push/rebase、base 漂移；workflow/validator/依赖/保护/ruleset、owner/collaborator、security/source-binding 能力变化；trusted-control audit 的输入、结果或证据变化；check rerun 或 check-run 的状态、结论、app、event、path、attempt、run/job/log provenance 变化；review 提交/编辑/dismiss、review finding 或 discussion 变化；以及 PR title/body/comment/label/draft/review request/auto-merge/queue/mergeability 变化。窗口结束后的临门快照仍须与起点完全一致。

## 9. 生效状态机与 bootstrap 边界

本决策不能授权自身。唯一状态机如下：

```text
PROPOSED / effective=PENDING
  -> 治理 PR 通过普通受保护合并
  -> 仍为 PROPOSED / PENDING
  -> 对已合并治理 commit 做独立、只读 post-merge 验证
  -> 独立 evidence PR 只回填先前治理 merge SHA、证据和状态字段
  -> evidence PR 通过普通受保护合并
  -> ACTIVE
```

Owner 在 2026-08-29 已明确表达“建立单维护者治理”的 bootstrap 决策意图，但该意图不是尚不存在候选的 exact authorization evidence。治理 PR 与 activation evidence PR 创建后，必须分别取得并回读 owner attestation，至少绑定 PR 号、base/head/tree、changed paths、风险、两路 review、trusted-control audit、checks、稳定窗口、例外和回滚；取得前状态为 `PENDING`，不得合并。

当该 exact attestation 经 API 逐字回读为 `VERIFIED`，且同一候选的两路 fresh Agent review、trusted-control audit、required checks 和稳定窗口全部为 `VERIFIED` 时，它只对该治理 PR 或 activation evidence PR 构成替代 v0.2 第二位人类前置的一次性 bootstrap authorization。任一项或其证据变化都会立即使 attestation/窗口失效。Attestation 仍不计入 verifier quorum，不是 GitHub `APPROVED` 或人类 review。PR #18 的 attestation 仅授权 CI-B0，不能复用于本治理 bootstrap；该一次性例外不得传播给 PR #17、业务代码、保护设置或生产操作。

两个 bootstrap PR 均按 `CR3` 执行；它们不得引用尚未 `ACTIVE` 的本决策为自身授权。Evidence PR 不得修改本决策的 context、options、decision、scope、风险分级或生产边界；若需要修改这些内容，必须新建精确 `supersedes` 决策并重新进入 `PROPOSED`。

`effective_commit` 在 evidence PR 中只能填写**先前治理 PR 的实际 merge commit**，不能填写 evidence PR 自身尚不存在的 merge SHA。Evidence PR 的候选内容即使写有 `ACTIVE`，也只有在其 normal protected merge 成功后才生效。

治理 docs-only PR 合并后，post-merge evidence 必须记录实际 merge commit/tree/parent、merged_at/by/method、保护快照和真实 workflow 结果。当前 Rust workflow 的 main push 有路径过滤；若 docs-only 变更未调度 Rust workflow，必须写 `NOT_SCHEDULED`，不能写 `PASS`。`design-contracts` 只记录实际 run 结果。

## 11. 不创建、不满足的外部门

本决策不声明以下编号已在当前 `main` 生效；它只明确：未来交付计划或外部变更单若采用这些门，单维护者仓库流程不能创建、满足或弱化它们。

- `H1`：Provider/数据准入，包括用途、合同/许可、地域、留存、预算和支持责任；
- `H2`：环境/凭据，包括环境所有权、最小权限 IAM、KMS/secret reference、轮换、审计和吊销；
- `H3`：安全/容量/恢复，包括威胁模型、独立安全评估、容量卡、RTO/RPO、备份恢复、故障域和 on-call；
- `H4`：发布窗口/变更单，包括制品、配置、allow-list、扩流、阈值、负责人、窗口、回滚和沟通；
- `H5`：最终 Go/No-Go，包括业务、工程、SRE、安全等具名人类责任；
- `H6`：上线后确认，包括观察窗、告警/事故、成本/计量和客户影响。

Agent 只能准备、校验和索引脱敏证据，不能获取生产凭据、代签、部署、扩流、执行不可逆 migration 或虚构外部结果。

## 12. 回滚与失败关闭

- 规范错误通过新的普通受保护 superseding/revert PR 修复；在替代内容进入 `main` 前，当前 `ACTIVE` 决策仍是事实，不能靠删除本地文件宣称回滚。
- 若 required context 或 workflow 被后续变更破坏，优先使用仍产生有效 context 的受保护 forward-fix PR。无法通过现有保护时保持阻塞；任何保护迁移都需要单独计划、用户对精确设置变更的明确授权和独立审计，不能使用 admin/force 绕过。
- `Finding-P0`、回滚不可执行、证据来源不明、main/base 漂移或保护快照变化时 fail closed。
- 回滚本决策不会自动回滚已合并业务代码、生产配置或外部状态；这些对象必须使用各自的恢复路径。
