范围：从当前 M1-05 工作树持续推进至受控生产发布与 GA 运营

## 1. 用途与执行约束

本文是[生产发布路线图](QingYin_生产发布路线图_2026-08-12.md)的执行层：路线图定义“什么条件下可以提升发布等级”，本文定义“下一批工作如何切分、谁可以做什么、用什么证据推进”。阶段范围、发布等级、双 Provider、生产状态和 Go/No-Go 硬规则仍以路线图为准；本文不降低任何出口条件。

持续推进遵循以下规则：

1. 以当前工作树、受保护分支、CI、目标环境和外部系统的现场结果为事实；历史交接只用于定位，不直接作为完成证据。
2. 每个 Goal 只有 `READY -> ACTIVE -> VERIFYING -> ACCEPTED` 四种正向状态；缺入口或证据时为 `WAITING`，门禁失败时为 `STOPPED`。不能以“代码已写”“本地通过”替代 `ACCEPTED`。
3. 关键路径一次只推进一个待验收 Goal；账号申请、合规、环境准备、观测和文档可并行，但不能提前宣称下游阶段完成。
4. 外部证据只能由对应真实系统或具名审批人产生。Agent 可以整理、校验、脱敏和建立索引，不得虚构 Provider 探针、云资源、账单、压测、恢复、客户同意、审批或生产发布结果。
5. Codex/Agent 不得自动执行生产发布、生产凭据启用、生产路由扩流、不可逆 migration、release tag 或 Go 签字。即使自动化检查全绿，也必须停在本文第 10 节的人工门前，取得本次操作的明确授权。

## 5. PR 切片与合并列车

### 5.1 通用切片规则

- 一个 PR 对应一个 Issue、一个可回滚行为和一个主要风险域；禁止把“顺手重构”、下一 Goal 或无关格式化混入。
- 公开契约、migration、鉴权/权限、计量、Provider 路由、生产配置和 IaC 分别切片，并把对应测试与变更同 PR 提交。
- 并行 PR 必须从同一个已验收 `main` 创建；不得互相复制未合并 commit。需要共同契约时先合并契约 PR，再重新基线化消费者分支。
- 每个 PR 描述必须列出：目标/非目标、允许路径、依赖、状态/安全/容量影响、fixture 或 migration、验证命令、回滚和未关闭项。
- 本地通过、已提交、已推送、PR checks 通过、review resolved、已合并、已部署是七种不同状态，证据账本不得合并表述。
- 高风险 PR（security、state/migration、admission、usage、Provider route、production config）必须有独立 reviewer；作者或实现 Agent 的自检不能替代审批。

## 6. Multi-Agent 协作边界

主 Agent 是唯一执行协调者，负责事实基线、工作分解、冲突处理、最终 diff、门禁和“是否可进入下一 Goal”的判断。子 Agent 只在明确的路径与产物边界内工作：

1. 每个子任务必须写明 Goal/Issue、允许修改路径、禁止范围、输入 commit、预期测试和“不得提交/推送/部署”等权限。
2. 同一时刻一个文件只有一个写入所有者。共享契约、Cargo lock、索引和 CI 默认归主 Agent；其他 Agent 对这些文件只提交建议或补丁摘要。
3. 代码实现、测试/故障注入、文档/证据、独立审阅可并行；审阅 Agent 不得直接把自己的发现标记为已解决，必须由写入所有者修复并由主 Agent 复验。
4. Agent 不得清理未知 dirty files，不得 reset/force push，不得覆盖用户改动，不得把另一个未合并分支的代码直接复制进关键路径。
5. 涉及租户隔离、认证、secret、计量、migration、Provider route、容量或生产配置时，至少安排一个未参与实现的审阅 Agent，并按严重级别记录发现。
6. 子 Agent 的“完成”仅表示其受托产物已交回；只有主 Agent 在完整工作树上复验后，才能改变 Goal 状态。
7. 所有 Agent 都只能准备生产操作清单、只读核验和脱敏证据；生产凭据获取、生产环境写操作、扩流、回滚和最终发布必须通过第 10 节人工门。

## 7. 验证矩阵与失败处理

每个代码 Goal 至少执行三层验证：

| 层级 | 内容 | 失败处理 |
| --- | --- | --- |
| 局部 | 目标 crate/模块的 fmt、check、test、契约或 migration 单测 | 留在当前 PR 修复，不以其它模块通过抵消 |
| 工作区 | locked/all-target/all-feature check、clippy、tests/doctest、rustdoc、boundary/fixture/design/link/secret | 阻止合并；基线自身失败时建立单独证据并先恢复基线 |
| 环境 | 临时真实 backend、sandbox Provider、负载/故障、生产灰度 | 阻止对应 R 阶段/发布等级；本地 fake 结果不能替代 |

Flaky、超时或环境错误仍是“未证明”，不能按通过处理。重跑必须保留首次失败、重跑次数、原因和修复；只有明确证明测试基础设施故障且由独立负责人接受时，才可从产品缺陷中分类出去。

## 8. 证据账本

每个 Goal 创建或更新 `QingYin_G<编号>_验收与复盘.md`；路线阶段关闭时再形成路线图要求的 `QingYin_R<阶段>_验收与复盘.md`。仓库只保存脱敏摘要和受控外部系统引用，不保存 secret、连接串、客户音频/全文或未脱敏账单。

证据条目使用以下字段：

| 字段 | 要求 |
| --- | --- |
| `evidence_id` | 稳定 ID，例如 `G3-STATE-RESTORE-001` |
| `requirement` | 对应 Goal 出口、测试项或人工门，不写模糊的“功能正常” |
| `source` | CI、GitHub、云控制面、Provider 控制台、工单、监控或审批系统 |
| `binding` | commit/tag、artifact digest、config hash、fixture hash、environment、provider/account/task/region/api revision |
| `execution` | 命令/操作、工具版本、执行时间、观察窗口和原始结果位置 |
| `result` | `PASS`、`FAIL` 或 `INCONCLUSIVE`；不得用空白表示通过 |
| `owner/verifier` | 产生者与独立核验者；人工审批必须是具名角色/记录 ID |
| `classification` | 可入库摘要、受限引用或禁止入库数据 |
| `valid_until` | 容量、Provider、安全、证书、备份/恢复和审批的失效时间/条件 |
| `status` | `MISSING`、`PENDING`、`GENERATED`、`VERIFIED`、`EXPIRED`、`REJECTED` |

只有 `VERIFIED` 且未过期的证据可用于阶段出口。尚未取得的外部证据必须显式写为 `MISSING`/`PENDING`，不能创建看似真实的 ID、时间、通过率或签字。配置、Provider/API、拓扑、容量、策略或制品发生变化时，受影响条目立即变为 `EXPIRED` 并回到对应 Goal。

## 9. 风险与决策日志

风险条目最少包含 `risk_id / description / trigger / impact / likelihood / owner / mitigation / fallback / review_date / status / evidence`。当前应持续跟踪：

| ID | 当前风险 | 触发/停止信号 | 处理方向 |
| --- | --- | --- | --- |
| RSK-001 | M1-05 dirty tree 与 PR 范围漂移 | 未跟踪文件漏入、用户 handoff 或 M1-06 行为被一起暂存 | 使用显式路径清单、`git diff --cached` 和验收账本；不使用 `git add -A` |
| RSK-002 | 生命周期候选契约尚无远端验收 | GitHub 独立审阅发现跨租户 mutation、矛盾补偿或 fake/trait 分歧 | 保持 `VERIFYING`，在同一 PR 修复并重跑完整矩阵 |
| RSK-003 | 外部账号、配额、地域、合同或数据条款延迟 | G4/G5 入口证据仍为 `MISSING` | A/E 工作流提前申请；不降低发布门 |
| RSK-004 | fake 与真实 PG/Redis 语义漂移 | contract suite 在真实 backend 失败 | 同一套 suite、故障注入、migration/restore 验证 |
| RSK-005 | 双 Provider 实际共享故障域 | 同云/网络/账号/API 控制面无法证明独立 | 故障域分析；不满足则保持 E1/LP |
| RSK-006 | 容量、成本或观测证据过期 | 快照/config/topology 改变或观察窗口不足 | 自动失效、停止扩流、回到 G5/G6 复测 |
| RSK-007 | M1-07 接受客户端选择 admission 维度 | DTO 可改变 pool/account/snapshot，导致容量或预算分桶绕过 | 仅允许服务端 canonical resolver 构造并持久化这些值；增加注入负测 |
| RSK-008 | reclaimer 延迟或积压造成许可长期占用 | oldest-expired age 超过两个周期/30 秒、满批持续或错误无告警 | 有界批处理、满批立即追赶、有界退避、租户公平性与 SLO 告警；R2/R6 重测 |
| RSK-009 | `rust-version = 1.85` 与 pinned Rust 1.97 证据不一致 | 代码只在 1.93/1.97 通过但未验证声明的 MSRV | 在 CI 增加 Rust 1.85 lane，或经兼容性决策更新 `rust-version`；不得互相替代证据 |

架构/交付决策使用 `DEC-YYYYMMDD-NNN`，至少记录 context、options、decision、rationale、owner、required approvers、effective commit/config、supersedes 和 evidence。当前冻结决策包括：M1 只用 fake、真实 PG/Redis 在 R2；单 Provider 最高为 E1 或有书面例外的 LP；PC/GA 每个发布能力需要双 Provider；生产发布必须通过人工门。改变这些决策必须新建 superseding decision，不能静默改表格或放宽测试。

## 10. 生产人工门

| 人工门 | 必须由人确认的内容 | Agent 可以做 | 未通过时的停止位置 |
| --- | --- | --- | --- |
| H1 Provider/数据准入 | 账号用途、合同/许可、地域、数据处理/留存、预算和支持联系人 | 准备清单、probe 脚本、读取脱敏结果 | G4 入口前 |
| H2 环境与凭据 | 环境所有权、IAM 最小权限、KMS/secret reference、轮换、审计和紧急吊销 | 校验引用/权限摘要；不得索取或回显明文 secret | 任何真实环境写操作前 |
| H3 安全/容量/恢复 | 威胁模型、安全评估、容量卡、RTO/RPO、备份恢复、双 Provider 和 on-call | 汇总证据并指出缺口 | G6 入口前 |
| H4 发布窗口/变更单 | 制品与 config、allow-list、扩流阶梯、阈值、负责人、窗口、回滚和沟通 | 生成 runbook/dry-run；不得实际扩流 | 生产部署前 |
| H5 最终 Go/No-Go | 业务、工程、SRE、安全联合签字及例外到期条件 | 根据证据建议 GO/NO-GO；不得代签 | 每次 canary 阶梯与 GA 前 |
| H6 上线后确认 | 观察窗口、告警/事故、成本/计量、客户影响、是否继续扩流 | 只读监控、整理复盘、建议回滚 | 下一扩流阶梯前 |

生产凭据只通过获批 secret manager 在指定任务/窗口注入；不得出现在对话、命令回显、文件、Git、CI artifact 或证据摘要中。任何 Agent 遇到未脱敏凭据必须停止传播、报告并走轮换流程。

明确授权必须针对本次环境、制品、变更单、窗口和操作范围；“持续推进到生产”不是无限期生产写权限。没有 H4/H5 时可以继续代码、测试、dry-run、文档和非生产环境工作，但必须停在生产变更前。

## 11. 每轮持续推进节奏

1. **取证**：重新记录 branch/HEAD/dirty、上轮证据状态、外部依赖和风险变化。
2. **选 Goal**：只把满足输入的最前关键路径 Goal 设为 `ACTIVE`；拆出不改变关键路径结论的并行工作流。
3. **分配**：按文件所有权委派 Agent；保留一个独立审阅槽；明确禁止范围和交付格式。
4. **实现与局部验证**：小步修复，保留失败记录；不跨 PR 边界补下游功能。
5. **集成验证**：主 Agent 在完整工作树和同一 commit 候选上执行工作区/环境矩阵。
6. **审阅与证据**：更新 evidence、risk、decision；让独立 reviewer 复核高风险不变量。
7. **状态转换**：只在所有出口和外部证据齐全后标记 `ACCEPTED`；否则保留 `ACTIVE/VERIFYING/WAITING/STOPPED` 并继续可行工作。
8. **发布停点**：到 H1-H6 中任一人工门时明确报告所需授权、风险、具体操作和回滚，等待人类决定，不自动越过。

当前下一动作是完成 G0 的不可变候选 commit 与单一 M1-05 PR，在固定 Rust 1.97 上取得 required checks、独立 reviewer 和 discussion resolution，并回填验收账本。G0 在这些证据齐全前保持 `VERIFYING`，生产保持 `NO-GO`；M1-06/07 只允许上述 readiness、账号/环境申请和证据模板准备。
