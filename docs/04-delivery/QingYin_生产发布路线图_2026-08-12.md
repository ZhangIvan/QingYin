# QingYin 生产发布路线图

版本：v0.1
状态：执行基线
审计日期：2026-08-12
范围：从当前 M1 开发基线持续推进到标准生产发布

## 1. 当前结论

当前生产判定为 **NO-GO**，当前最高允许等级为 `D0 开发验证`。项目可以继续完成 M1 的 MockProvider 纵向切片，但不得宣称已具备真实 Provider、生产状态存储、生产容量或高可用能力。

关键路径为：

```text
R0 事实恢复与源码归一
 -> R1 M1 可测核心
 -> R2 PostgreSQL/Redis 生产状态
 -> R3 首个 Provider experimental
 -> R4 真实纵向切片与内部 Alpha
 -> R5 第二 Provider 与切换演练
 -> R6 生产安全、容量与恢复
 -> R7 受控生产灰度
 -> R8 标准生产与持续运营
```

阶段不得按日期自动升级；只有入口条件、实施项、出口条件和外部证据同时满足，才允许进入下一阶段。详细验收口径继续以[测试验收与发布计划](../02-architecture/QingYin_测试验收与发布计划.md)、[M1 Backlog 与 CI 门禁](QingYin_M1_实施Backlog与CI门禁.md)及模块 09、10、14、15 为准。

## 2. 审计事实基线与 NO-GO

以下是 2026-08-12 的审计切面；R0 必须在每次换机、复制源码或恢复工作后重新生成事实记录。

| 事实 | 已核对证据 | 发布含义 |
| --- | --- | --- |
| 当前分支为 `feat/m1-05-admission-lifecycle`，审计时 HEAD 为 `8116552`，与 `origin/main` 一致 | 本地 Git 分支、日志和 remote | M1-05 工作树不是已合并发布证据 |
| M1-01/02、M1-03、M1-04 分别有 `c962a05`、`d76bf88`、`8116552` 历史 | Git 历史及既有 PR 记录 | 可作为 R1 前置，仍需在当前 HEAD 回归 |
| M1-05 存在未提交的 admission 实现 | `qingyin-admission` 工作树 | 必须完成编译、测试、审阅、CI 和 PR，不能按“已开工”计完成 |
| `qingyin-state` 仅定义存储语义，`qingyin-testkit` 提供确定性内存 fake | crate README 与实现 | 尚无生产 PostgreSQL/Redis backend；生产 NO-GO |
| `qingyin-provider` 尚未实现真实 Adapter | crate 实现与 M1-06 计划 | 尚无 sandbox Provider，更无主备；真实流量 NO-GO |
| 仓库已有 Rust、fixture、边界、secret、设计与链接门禁 | `.github/workflows/` 与 `scripts/` | 是内部证据入口，不替代真实环境、Provider、压测和演练证据 |
| 源码由 Windows 直接复制到 Linux 服务器 | 用户交接事实 | R0 必须检查 CRLF/BOM、大小写冲突、执行位、忽略文件和未跟踪文件，禁止无差别重写 |

当前未具备的生产必要证据包括：真实 PostgreSQL/Redis 一致性与恢复、真实 Provider 能力快照、第二 Provider、目标环境容量卡、N+1、主备切换、外部安全评估、数据/留存审批、生产灰度与回滚记录。因此当前不能进入 limited preview、production canary 或 GA。

## 3. 发布等级与 Provider 硬规则

发布等级与 R0-R8 路线阶段是两个维度：阶段说明工程进度，等级说明允许承载的流量。

| 等级 | 允许范围 | Provider 条件 | 明确禁止 |
| --- | --- | --- | --- |
| `D0 开发验证` | 本地、CI、合成数据 | MockProvider | 真实客户流量、SLA、生产能力宣称 |
| `E1 Experimental` | sandbox、内部或具名灰度租户显式选择 | 1 个通过模块 09 experimental 门的真实 Provider | 默认路由、无提示开放、生产 SLA |
| `LP 受限预览` | 有时限、租户 allow-list、硬配额的真实小流量 | 原则上 2 个；单 Provider 仅允许书面例外 | 默认开放、GA、把例外描述成标准生产 |
| `PC 生产灰度` | 可回滚的小比例生产流量 | 每个已发布能力至少 2 个合格且外部故障域独立的 Provider | 单 Provider、无切换演练、无有效容量卡 |
| `GA 标准生产` | 经批准的默认路由和公开服务范围 | 双 Provider 持续满足 enabled、SLO、容量与切换门 | 证据过期后继续扩流、绕过 Go/No-Go |

Provider 数量按 `provider_id + task + region + account_scope + api_revision` 的准入对象和已发布能力分别计算。若同时发布 ASR 与 TTS，两项能力都必须各自具备主、备；同一 Adapter 换两个密钥、模型或账号不自动构成独立 Provider，必须用故障域分析证明独立性。

首个真实 Provider 只能提升到 `E1 Experimental`，不能进入默认生产路由。单 Provider 承载真实流量的唯一例外是 `LP 受限预览`：业务负责人、技术负责人、SRE 和安全负责人必须书面接受上游整体不可用风险，写明到期时间、具名租户、流量上限、无生产 SLA、监控和一键关闭方式。该例外不能豁免租户隔离、密钥安全、数据保护、生产状态存储或未关闭 P0，也不能直接升级到 GA。

## 4. M1 fake 与 PostgreSQL/Redis 的阶段决议

本路线图作出以下冻结决议，解决既有文档中“真实 Postgres/Redis 属于 M1 验收”与“M1-03 只交付内存 fake”的冲突：

1. M1/R1 只交付存储 trait、事务/TTL/幂等语义、确定性 fake 和可复用 contract suite；它证明设计语义可测，不证明生产存储成立。
2. 真实 PostgreSQL/Redis Adapter、migration、连接与 secret、故障恢复、备份恢复和并发一致性全部迁移到 R2。任何把这些工作倒灌进 M1 的变更都需重新拆分边界。
3. M1 验收包中的“Postgres/Redis 状态一致性”改按“待 R2 关闭的强制项”记录；R1 只附相同语义在 fake 上的结果，不得用 fake 结果代替真实存储报告。
4. R2 必须让同一套状态 contract suite 分别运行在 fake、临时 PostgreSQL 和临时 Redis 上，并增加事务冲突、原子消费、进程中断、网络故障、migration 和恢复测试。
5. `production` profile 必须在配置解析或启动时拒绝任何内存 state；健康信息要能证明 backend 类型和 migration 版本，但不得暴露连接串或 secret。

本决议优先于此前把真实 PG/Redis 放进 M1 的措辞；后续修订相关文档时只做状态对齐，不改变上述边界。

## 5. R0-R8 执行路线

### R0：事实恢复与源码归一

- **入口**：本地 checkout、原始复制来源和远端仓库均可访问；先保护用户未提交改动。
- **实施**：记录 branch、HEAD、remote、dirty files 和提交包含关系；核对 Windows 复制带来的 CRLF/BOM、文件名大小写冲突、可执行位、symlink、生成物、锁文件和 secret；仅对有证据的问题做最小修复；运行现有 Rust、fixture、boundary、secret、design、link 基线。
- **出口**：不存在未解释的来源差异或文件损失；修复 diff 已审阅；事实报告绑定 commit；可运行的基线检查全绿，不能运行的检查有负责人和阻塞记录。
- **外部证据**：GitHub 上对应 commit/分支/required checks、远端保护规则，以及源码复制或恢复来源的确认记录。

### R1：M1 可测核心闭环

- **入口**：R0 通过；M1-01 至 M1-04 的历史与当前 HEAD 回归一致。
- **实施**：按独立 PR 完成 M1-05 至 M1-11，包括 admission、Provider Runtime/MockProvider、Control Gateway、Relay、one-shot TTS、用量/观测和发布证据；保持 bounded queue、幂等释放、租户隔离和脱敏边界。
- **出口**：M1-01 至 M1-11 全部关闭；fixture、MockProvider profile、取消/超时、usage/outbox、secret 和 workspace 门禁全绿；形成 `QingYin_M1_验收与复盘.md`；限制明确写为“仅 mock”。
- **外部证据**：GitHub PR、resolved review、required checks、milestone、commit/config/fixture hash 和可追溯构建制品。

### R2：生产状态与部署底座

- **入口**：R1 的 State/Security/Admission 契约冻结；可获得隔离的 PostgreSQL、Redis、secret manager 和 CI 集成环境。
- **实施**：实现 PostgreSQL durable adapter、Redis TTL/atomic adapter、migration/outbox worker、连接池与 TLS/secret reference、生产 profile guard、备份恢复和观测；用同一 contract suite 验证 fake 与真实 backend。
- **出口**：事务、租户隔离、reservation/outbox、ticket 单次消费、TTL、并发冲突和补偿在真实 backend 通过；migration 前进/回退方案可执行；进程、网络、主从/节点故障及备份恢复演练达到已批准 RTO/RPO。
- **外部证据**：实际服务版本和拓扑、IAM/KMS/secret 轮换记录、备份对象与恢复时间戳、故障演练和云资源配置 ID；仓库只保存脱敏索引。

### R3：首个真实 Provider Experimental

- **入口**：R2 集成环境通过；首个 Provider 的 sandbox 账号、合同/测试许可、地域、凭证托管和预算就绪。
- **实施**：实现首个 Adapter、canonical 错误映射、取消/超时、限流/熔断、成本计量和 feature flag；按[模块 09](../02-architecture/modules/QingYin_模块09_Provider准入探针与能力目录.md)至少完成 PV-001 至 PV-010 并生成不可变能力快照。
- **出口**：Provider 最高标记为 `experimental`；仅具名内部/灰度租户显式选用；不在默认路由；无生产客户数据；配额、错误、成本和回滚开关均可观测。
- **外部证据**：Provider 账号与权限确认、sandbox probe、API/模型/地域版本、配额与账单样本、数据处理/留存条款和支持联系人。

### R4：真实纵向切片与内部 Alpha

- **入口**：R3 能力快照有效；真实 Gateway/Relay 路径、SDK 测试客户端和合成或已授权语料可用。
- **实施**：打通鉴权、准入、路由、真实 Provider、流式事件、取消、用量/outbox、审计和告警；执行 SDK/浏览器/服务端互操作、慢消费者、断链、429、超时和成本对账。
- **出口**：内部 Alpha 在批准观察窗口内满足阶段 SLO；资源和 reservation 可收敛；Provider 请求 ID 与内部用量可对账；无未关闭 P0；仍保持 `E1 Experimental`。
- **外部证据**：有授权的测试素材清单、真实客户端互操作结果、Provider request ID/账单样本、内部租户验收和问题关闭记录。

### R5：第二 Provider 与切换演练

- **入口**：R4 稳定；第二 Provider 的独立账号/故障域、凭证、预算和 sandbox 权限就绪。
- **实施**：接入第二 Adapter，复用相同 canonical fixture 和模块 09 探针；实现候选路由、独立熔断、配额/成本闸门、策略降级和一键回滚；演练建连前主备切换，并保持流中音频不隐式重放。
- **出口**：每个拟生产能力有 2 个通过 `enabled` 门槛的独立候选；主 Provider 故障时新会话按目标切换或确定拒绝，无无限重试、跨租户影响或重复计量；恢复和切回同样有记录。
- **外部证据**：两套独立 Provider 准入报告、真实配额/地域/支持范围、故障域分析、受控切换工单、trace/metric/账单和回滚结果。

### R6：生产安全、容量与恢复

- **入口**：R2 生产状态和 R5 双 Provider 均通过；目标生产拓扑、流量画像和责任人已确定。
- **实施**：完成多故障域部署、Edge/WAF/TLS、secret 轮换、威胁模型与外部接口安全测试、SBOM/签名/漏洞策略、日志与隐私审计；按[模块 10](../02-architecture/modules/QingYin_模块10_环境容量卡与能力发布.md)生成容量卡并执行混合压测、N+1、备份恢复和[模块 14](../02-architecture/modules/QingYin_模块14_生产安全与高可用恢复.md)故障演练；建立监控、告警、on-call 和 runbook。
- **出口**：容量卡有效且路由上限不超过 `capacity_safe`；实际 RTO/RPO 和 SLO 经批准；无未关闭 P0，P1 有明确负责人/期限/接受人；发布、回滚、Provider 切换、状态恢复和密钥轮换均可复现。
- **外部证据**：云拓扑与配额、压测原始报告、恢复/切换工单、第三方或独立安全评估、数据分类/留存/合规审批、on-call 值班与发布责任确认。

### R7：受控生产灰度

- **入口**：标准路径必须通过 R6；单 Provider 例外必须已通过 R2/R4 及 R6 中除双 Provider 外的全部门，并具备第 3 节规定的书面、限时风险接受。
- **实施**：按变更单定义的 allow-list 和小比例真实流量发布；冻结版本、配置、Provider 与容量快照；逐级观察 SLO、错误、成本、隔离和告警，验证自动/人工回滚。证据不足时降权或关闭，不以扩大流量补样本。
- **出口**：标准双 Provider 灰度在批准观察窗口内达标且无 P0，才可申请 R8；单 Provider 路径只能维持 `LP 受限预览`，到期必须关闭或回到 R5/R6 后重新灰度，不能直接进入 R8。
- **外部证据**：发布审批和变更单、具名租户/必要的客户同意、实时仪表盘快照、告警/事故记录、回滚演练、业务/SRE/安全联合结论。

### R8：标准生产与持续运营

- **入口**：R7 标准双 Provider 灰度通过；GA 服务范围、SLO/支持边界、容量、值班、状态沟通和回滚责任均已批准。
- **实施**：从签名 release tag 和不可变制品逐级扩流；只开放已通过门禁的 task/region/profile；持续检查 Provider 快照、容量卡、证书、漏洞、成本、备份和演练有效期。
- **出口**：GA 发布记录完整，默认路由、配额和公开承诺与有效证据一致；完成上线复盘。R8 不是永久通行证，任一关键证据过期或 SLO 失守即停止扩流并降级到相应等级。
- **外部证据**：最终 Go 签字、release/tag/制品证明、SLA/支持和状态沟通材料、生产变更记录、上线后观测与复盘。

## 6. 证据包与持续推进规则

每个 R 阶段均新增 `QingYin_R<阶段>_验收与复盘.md`，至少记录 commit/tag、配置与 fixture hash、环境和工具版本、执行时间、命令与结果、风险、负责人、外部证据 ID、回滚方式和最终结论。外部证据是仓库外真实系统产生的 Provider、云资源、账单、审批、安全评估、压测或演练记录；CI 不能代替它，也不得由实现者虚构。

证据只保存脱敏摘要和受控系统引用，禁止提交凭证、连接串、客户音频/全文或未脱敏账单。能力快照、容量卡、Provider 配额、Adapter/模型/API 版本、基础设施或策略发生变化时，相关证据自动失效，必须回到对应阶段复测。

执行上只允许一项关键路径工作处于“发布结论待定”；账号申请、合同/合规评审和目标环境准备可提前并行，但不能被计作阶段完成。代码工作仍按小 PR、独立审阅、required checks 全绿后合并；本地通过、已提交、已推送、已合并和已发布必须分别报告。

## 7. Go / No-Go

发布负责人召集工程、SRE、安全和业务负责人作出 `GO`、`CONDITIONAL GO` 或 `NO-GO`。`CONDITIONAL GO` 必须写明条件、到期时间、责任人和自动降级动作；到期未关闭自动转为 `NO-GO`。

满足以下全部条件才可对目标等级判定 GO：

1. 目标阶段入口、实施、出口及外部证据完整，且绑定同一 release/config/环境。
2. required checks、契约、状态、安全、secret、性能和回滚检查全绿，无未经解释的基线放宽。
3. 生产 profile 使用真实 PostgreSQL/Redis，migration、备份恢复和 RTO/RPO 证据有效。
4. `PC/GA` 的每个已发布能力具备双 Provider、有效能力快照和切换演练；单 Provider 只按限时 LP 例外处理。
5. 容量卡有效，限流/告警/路由不超过 `capacity_safe`，N+1 与降级路径已演练。
6. 无未关闭 P0；密钥、租户隔离、数据保护、计量、回滚和 on-call 责任明确。

出现以下任一情况立即 NO-GO：

- 未审阅 dirty tree、release 不来自通过检查的受保护分支/tag，或制品无法追溯。
- production 配置可选择内存 fake，或真实状态一致性、migration、恢复证据缺失。
- 单 Provider 进入默认生产路由、LP 例外缺失/过期，或所谓主备属于同一未隔离外部故障域。
- Provider/容量/安全证据过期，SLO、错误率、成本或资源水位超过批准阈值。
- 存在 secret/客户数据泄漏、跨租户访问、重复计费/静默丢账、不可回滚 migration 或未关闭 P0。
- 没有可执行回滚、监控告警、值班责任或客户影响沟通方案。

租户隔离、secret/客户数据泄漏、不可恢复数据损坏和未关闭 P0 不得通过风险接受豁免。单 Provider 的书面例外仅改变可用性风险结论，不改变其它生产门禁。
