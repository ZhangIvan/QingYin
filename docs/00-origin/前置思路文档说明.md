# 项目总结：基于 SenseVoiceSmall + MeloTTS 的高可用语音服务构建方案 - 轻音（QingYin）

## 一、项目目标

基于 **SenseVoiceSmall (ASR)** 和 **MeloTTS (TTS)** 两个“小而美”的模型，打造一个**高可用、低延迟、低资源占用**的生产级语音识别与合成服务，支持大规模并发调用。

## 二、核心模型能力评估

| 维度 | SenseVoiceSmall (ASR) | MeloTTS (TTS) |
|------|----------------------|---------------|
| **资源占用** | CPU可运行，识别速度17.2倍实时 | CPU可运行，单次合成中文约90ms |
| **流式支持** | ✅ 原生支持（非自回归架构） | ⚠️ 需工程实现（基于流的架构可实现分块流式） |
| **大规模调用潜力** | 需工程化部署（FunASR框架可承载） | 单实例（4核）可支撑200+并发 |
| **模型格式** | PyTorch，支持导出ONNX | PyTorch，存在ONNX实现 |

## 三、技术选型决策树

### 方案A：FastAPI + Python（快速验证路径）
- **优势**：开发效率极高，与PyTorch生态无缝集成，成熟案例多
- **局限**：受GIL限制，高并发下有性能天花板
- **适用阶段**：POC验证、原型开发

### 方案B：Go/FastAPI 混合架构（生产推荐）
- **架构**：Go构建API网关（控制面）→ gRPC/消息队列 → FastAPI Worker池（推理面）
- **优势**：Go的轻量级协程处理高并发，Python负责模型推理
- **适用阶段**：生产环境高可用部署

### 方案C：Rust 独立部署（极致性能路径）
- **关键前提**：将模型转为ONNX格式（SenseVoice官方已支持导出）
- **成熟方案**：`lele` 推理引擎——纯Rust实现，专为SenseVoice等语音模型优化，**比ONNX Runtime快1.15倍，可达Python的2倍性能**
- **挑战**：预处理逻辑需与Python保持一致，学习曲线陡峭
- **适用阶段**：追求极致低延迟、低占用的高负载生产环境

### 方案D：Go 独立部署（折中路径）
- **可行性与框架**：已有`Born`、`Hugot`、`onnx-gomlx`等ONNX运行时，存在工程化实践
- **挑战**：生态相对年轻，若通过CGO调用C++库会有性能开销
- **适用阶段**：团队熟悉Go且不愿承受Rust学习成本时的备选

## 五、关键性能优化手段

1. **模型优化**
   - ONNX导出与量化（FP32→INT8/FP16），体积减少30-50%，速度提升20-40%
   - Rust路径可进一步做AOT预编译优化

2. **服务优化**
   - 全局单例模型实例（避免重复加载）
   - 动态批处理（攒批送GPU/CPU）
   - 异步接口 + 轮询结果（长任务解耦）

3. **运维保障**
   - Docker容器化 + K8s编排
   - 服务注册与发现（Consul/Etcd）
   - 进程守护（Supervisor）
